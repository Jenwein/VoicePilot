## 桌面语音助手项目总结与 V2.0 迭代规划

### 一、 相关问题思考

1.  **架构设计与权衡 (Architecture)**
    * **C++/Python 职责划分**：为什么选择 C++ 嵌入 Python？C++ 负责高性能、UI 和系统调用，Python 负责 AI API 交互，这个边界是如何决定的？
    * **GIL 处理**：`PythonGILRelease` 为何是必须的？它如何解决了主线程（UI）和后台线程（AI 处理）之间的锁竞争？
2.  **异步流程与状态管理 (Async & State)**
    * **核心状态机**：`AgentCore` 如何驱动 `Idle` -> `Listening` -> `Processing` -> `Speaking` 的流转？`OnUpdate` 在异步任务（`m_ProcessingTask`）的回调中扮演什么角色？
    * **取消操作**：`CancelOperation` 是如何安全中断一个正在进行的 `VoiceProcessingPipeline` 的？
3.  **AI 与工具链 (AI & Tool-Chain)**
    * **工具定义与执行**：C++ 中的工具定义（`ITool::GetDefinition`）是如何被收集并传递给 Python 端 的？Gemini 的工具调用结果如何路由回 C++ 的 `ToolRegistry` 执行？
    * **错误处理**：如果 `ai_service.py` 在调用 API 时失败，C++ 层的 `AIServiceWrapper` 是如何捕获和报告这个错误的？
4.  **底层模块实现 (Implementation)**
    * **音频处理**：`miniaudio` 的数据回调 (`recording_data_callback`) 是如何实现实时录音数据捕获的？
    * **UI 交互**：你是如何实现点击 3D 模型（`m_VoiceAssistantEntity`）来触发录音的？（涉及 `m_Framebuffer->ReadPixel` 实体拾取）。
5.  **鲁棒性与项目难点 (Robustness)**
    * **系统安全**：`Tools.cpp` 中的高危工具（如 `CloseProcessTool`）存在哪些安全隐患？LLM 是否可能生成有害的参数？
    * **最大挑战**：在 C++ 和 Python 之间管理线程、GIL 和异步回调是否是你遇到的最大困难？

### 二、 V2.0 核心迭代规划 (高优先级)

以下是 V2.0 迭代中应优先实现的核心架构升级和功能：

#### 1. 架构基石：事件总线 (Event Bus)

* **需求**：引入一个全局的“发布-订阅”事件总线。
* **目的**：
    * **彻底解耦**：`EditorLayer` (UI) 和 `AgentCore` 不再需要互相持有实例。UI 只需 `Publish(StartListeningRequest{})`，`AgentCore` 负责 `Subscribe` 该请求。
    * **消除回调地狱**：移除 `AudioManager` 中的 `onPlaybackFinished` 回调，改为 `Publish(PlaybackFinishedEvent{})`。任何关心此事件的模块（`AgentCore`、UI 动画模块等）都可以自由订阅，易于扩展。

#### 2. 架构演进：多 Agent 系统 (Multi-Agent System)

* **需求**：将当前的单体 `AgentCore` 重构为一个“总控 Agent” (OrchestratorAgent)，并剥离出多个“专家 Agent”。
* **目的**：
    * **职责分离**：`AgentCore` 会变得极其臃肿。应拆分为：
        * `ToolingAgent`：专门负责安全执行 C++ 工具。
        * `WebAgent`：专门负责执行网络搜索等（可集成 V2.0 规划中的 Google Search）。
        * `MemoryAgent`：专门负责历史对话和上下文管理。
    * **并行处理**：总控 Agent 可以将用户任务（“查天气并打开记事本”）并行分发给 `WebAgent` 和 `ToolingAgent`，提高效率。

#### 3. 协作协议：Agent 通信标准 (MCP)

* **需求**：基于事件总线，定义一套标准化的 Agent 间通信协议（MCP - Multi-Agent Collaboration Protocol）。
* **目的**：这是你提到的“MCP”的关键。如果 `WebAgent` 和 `ToolingAgent` 要协作，它们必须“说同一种语言”。
    * **标准化事件**：定义所有 Agent 必须遵守的事件结构（如 JSON Schema），包括 `TaskRequestEvent`, `TaskResultEvent`, `TaskFailedEvent` 等。
    * **服务发现**：允许 Agent 在启动时向总线“注册”自己能处理的任务类型。

#### 4. 核心性能优化

* **内存音频流**：**(高优先级)** 移除 `input.wav` 和 `output.wav` 的磁盘 I/O。`AudioManager` 应直接将录音的 PCM 数据块传递给 `AIServiceWrapper`，并能直接播放在 Python 传回的音频字节流。
* **端到端流式处理**：实现 ASR -> LLM -> TTS 的全流程流式处理，以实现最低的“首包延迟”（Time To First Byte），让助手几乎能立即响应。

#### 5. 核心体验与安全

* **语音唤醒 (KWS)**：实现本地、低功耗的语音唤醒词检测，使助手能常驻后台。
* **上下文打断 (Barge-in)**：允许用户在助手说话时 (Speaking 状态) 随时打断并开始新的 `Listening` 流程。
* **安全沙盒与权限**：**(高优先级)**
    * 为 `ExecuteShellCommandTool` 等高危工具建立沙盒。
    * 实现“人类在环”（Human-in-the-Loop）机制，对于删除文件、关闭进程等操作，必须弹窗由用户二次确认。

### 三、 未来功能展望 (中低优先级)

以下功能在 V2.0 核心架构稳定后进行探索：

* **AI 核心**
    * **长期记忆**：实现对话历史的序列化和加载。
    * **RAG 集成**：引入本地向量数据库，使助手能“学习”本地文档。
    * **AI 自我纠错**：当工具调用失败时，Agent 能分析失败原因并尝试重试或更换工具。
* **工具系统**
    * **插件化**：将 `Tools.cpp` 重构为动态插件系统（如 .dll/.so 或 Python 脚本），支持热加载。
    * **跨平台封装**：将 `Tools.cpp` 中所有 `#ifdef _WIN32` 的实现抽象到跨平台接口后。
    * **集成 Gemini 原生工具**：利用 `ai_service.py` 调用 Gemini API 自带的 Google Search、代码执行器等。
* **性能**
    * **本地化 AI**：调研并集成轻量级的本地 ASR (如 Whisper.cpp) 和 TTS (如 Piper) 模型，以消除网络延迟。
* **用户体验**
    * **精细化动画**：优化 `UpdateVoiceAssistantModel` 中的动画表现，使其更生动。
    * **应用上下文感知**：利用 `GetActiveWindowTool` 让 Agent 感知用户当前活跃的应用，提供更智能的帮助。
